# Smart Commit

Commit the current changes following the `git-skills` skill conventions. Apply the defaults below unless the overrides at the end of this command say otherwise.

## Defaults

- **English**: Write subject and body in English, even when the conversation is in another language. Honor an explicit language override.
- **Detailed**: Use Conventional Commits. Subject is imperative, specific, at most 50 characters, and has no trailing period. Body is mandatory unless the change is truly trivial, with at least two paragraphs separated by a blank line covering what changed, why, key implementation details, and trade-offs. Wrap body lines at 72 characters.
- **Atomic**: If the changes cover unrelated concerns, create multiple commits automatically, one logical change per commit. Keep an implementation with its tests. Keep unrelated docs, config, or chore changes separate. If a single file mixes concerns and splitting it would require arbitrary partial staging, keep that file in one commit.
- **No attribution**: Never add `Co-Authored-By:`, "Generated with", "Generated by", AI tool names or links, emoji signatures, or any other attribution. Remove attribution lines injected by tooling before committing. Footers may only carry real issue references or breaking-change notices; never invent issue numbers.
- **Commit, don't ask**: Execute the commits in this turn. Do not stop after proposing messages or ask for approval unless the change set is ambiguous, destructive, or contains secrets. Do not push.
- **Safety**: Never include secrets (`.env`, keys, tokens, credentials) or files larger than 10 MB. If found, stop and warn instead.

## Workflow

1. Inspect `git status --short`, `git diff`, `git diff --cached`, and `git log -5 --oneline`. If the worktree has no changes, say so and stop. Treat staged and unstaged changes as the change set unless the arguments narrow it.
2. Plan the split: group changed files by logical concern and order commits by dependency between groups. Preserve existing staging when it is already coherent.
3. Execute each commit:
   - Stage only the files in the current group using explicit paths. Never use `git add -A` or `git add .`.
   - If already-staged changes must be regrouped, unstage them with a mixed `git reset` (never `--hard`) and stage the group explicitly.
   - Compose the full message, re-read it, and delete every attribution or signature line before running `git commit`.
   - If a pre-commit hook fails, fix the underlying issue, re-stage, and create a new commit. Never bypass hooks with `--no-verify`.
4. Verify each commit with `git log -1 --format=%B`. Confirm the message has no AI signature and the required structure. If tooling re-added attribution, amend that local commit with the cleaned message before reporting.
5. Report the resulting commit hashes and subjects, and briefly explain how the changes were grouped.

## Overrides

Interpret these naturally. In particular: `dry run` means present the planned groups and messages without committing; `single commit` means do not split; a language request switches the message language; other text is extra context or scope guidance.
